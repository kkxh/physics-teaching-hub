# 长期路线

> 状态：**Phase 0 已完成（骨架）**，下一步进入 Phase 1。
> 本文件是所有长期对话的路线锚点：换会话、换 agent 时先读这里。

## 定位（不要偏离）

- 本仓库是作者私有教学系统的**开源精简版**：只做通用能力 + 虚构演示数据。
- **功能长期落后于上游是预期状态**，不追求功能对等；追赶不是目标。
- 上游私仓不在本仓库内，也不作为本仓库的远端。搬运是单向的：上游 → 本仓库。

## 仓库与发布状态

- 远端：`github.com/kkxh/physics-teaching-hub`，托管在 GitHub，**当前为私有仓库**。
- 默认分支 `main`；推送后 GitHub Actions 会运行测试、演示数据自检与隐私扫描。
- 推送政策：开发过程中可以正常推送；**转公开、打 tag、发 Release 必须由维护者明确批准**。
- 发布节奏：Phase 4 完成后才把仓库转为公开。
- 发布前硬性待办：补依赖许可清单；对全部历史做一次隐私扫描。（`LICENSE` 版权署名已于 2026-09-21 填为 DW YE。）

## 阶段

### Phase 0 — 骨架（已完成）

- 许可证、README、默认拒绝清单（`.gitignore`）
- 配置外置入口（`config.example.toml` + `config_loader.py`，学段已预留初中/高中）
- 虚构演示数据生成器（`seed_demo_data.py`）
- 隐私扫描（`scripts/privacy_scan.sh`）与 CI（`.github/workflows/ci.yml`）
- 搬运台账（`docs/MIGRATION_LEDGER.md`）

验收：测试全绿、演示数据自检通过、隐私扫描通过。

### Phase 1 — 通用化地基

目标：从「某位老师的私有系统」变成「任何物理老师都能部署的引擎」。

小步清单（每步一次提交）：

1. 配置全覆盖：学期、课表起点、周次、时区、数据库路径全部走 `config.toml`；环境变量可覆盖。
2. 路径与时间：消除绝对路径假设，所有路径相对配置解析。
3. 班级与阶段：把「教学跑道」抽象成可配置的阶段定义，学段（初中/高中）决定默认 profile。
4. 学科文案收口：散落的学科与学段字样收进配置或 labels 文件。
5. 首次可运行：能用虚构数据完成「建库 → 导入成绩 → 生成一份报告」的最小闭环。

验收：全新机器 clone 后，三条命令能看到基于虚构数据的输出。

### Phase 2 — 逐模块搬运（长期主线）

一次只搬一个模块，按「纯逻辑 → 数据层 → 业务动作 → 分析与输出 → 界面」的顺序推进。
每个模块的完成定义见 `AGENTS.md` 第 4 节，进度记入 `docs/MIGRATION_LEDGER.md`。

验收（累进）：每完成一批，仓库能跑通一条端到端演示流程。

### Phase 3 — 题库与教材隔离

- 只搬「框架」：题目结构、导入器、检索与推荐接口。
- 示例题必须自制，数量控制在十几道，够演示即可。
- 使用者的真实题库由使用者自己导入；仓库提供 `data/README.md` 说明格式。

### Phase 4 — 文档与发布

- 面向陌生读者的 README、架构说明、演示截图（全部虚构数据）。
- CHANGELOG、CONTRIBUTING、依赖许可清单。
- 发布前审计：填写 LICENSE 署名、跑一遍隐私扫描、检查 git 历史与依赖许可。
- 发布 v0.1.0-alpha，明确标注早期阶段。

### Phase 5 — 长期双轨维护

- 每月一次「搬运日」：从上游挑 1～3 个通用改进搬进来。
- 每季度回顾台账：连续三个月没动的模块，明确「放弃」或「降级」。
- 上游修复回灌只能人工进行，且只改通用逻辑。

## 接手顺序（给新会话）

1. 读本文件，确认当前阶段；
2. 读 `docs/MIGRATION_LEDGER.md`，看哪些模块搬过、差异是什么；
3. 读 `docs/PRIVACY.md`，确认不可跨越的边界；
4. 按 `AGENTS.md` 的工作方式开一个小步任务，先给出清单再动手。

- 每完成一个阶段或改变阶段目标时更新本文件顶部的「状态」。
- 阶段范围变化要写清原因，不要悄悄扩大范围。
